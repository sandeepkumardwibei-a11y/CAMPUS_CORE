## Detailed Descriptions

### 1. Module 4.1 — Identity & Access Management

This module forms the security backbone of the entire CampusCore system. It handles registration of every type of user in the application — applicants, students, faculty, examination controllers, accounts staff, and administrators — each assigned a specific role. Role-Based Access Control (RBAC) is implemented so that every API endpoint checks the logged-in user's role before allowing access, ensuring a student cannot access faculty-only endpoints and vice versa. Authentication is handled using JWT tokens, where a user logs in once and receives a token that is validated on every subsequent request. The module also enforces program-scoped data access, meaning users can only view or modify data relevant to their own department or program in a multi-campus setup. An AuditLog entity tracks every significant action performed by any user, capturing the action type, the module it occurred in, and a timestamp — this is critical for accountability and traceability. User status is also tracked (Active, Alumni, Suspended, Inactive) to control login eligibility. This module was built first since every other module depends on it for authentication and authorization. The Service layer handles password encryption, token generation, and role validation logic, while the Repository layer manages CRUD operations on the User and AuditLog tables. Unit tests for this module focus heavily on validating that unauthorized access attempts are correctly rejected.

### 2. Module 4.2 — Admissions Management

This module digitizes the entire admission process from application submission to enrollment confirmation. Prospective students submit applications specifying the program they wish to apply for, along with personal details and their qualifying score from the entrance exam or prior academic record. The system stores each application with a status field that moves through a defined lifecycle: Submitted, Shortlisted, DocumentsVerified, OfferIssued, Enrolled, Rejected, or Withdrawn. University admins or admissions staff can review applications, shortlist candidates based on merit (sorted by qualifying score), and trigger document verification workflows. Once verified, an OfferLetter is generated and issued to the applicant, containing the program details, fee reference, and a joining deadline by which the applicant must accept the offer. If the deadline passes without action, the offer automatically lapses. The Program entity defines available courses of study including their level (UG/PG/PhD/Diploma), duration, and total seat capacity, which the admissions logic checks against before allowing further shortlisting. This module required careful handling of status transitions to prevent invalid state changes (e.g. issuing an offer to a rejected application). The Service layer contains validation logic to ensure business rules are not bypassed, and Mockito-based unit tests verify that each status transition behaves correctly under different input scenarios.

### 3. Module 4.3 — Academic Registration & Course Management

Once a student is enrolled, this module manages their academic journey each semester. It allows students to register for a semester, which triggers course allocation based on the program's defined curriculum. The Course entity stores details such as course name, course code, credits, the assigned faculty member, and a maximum enrollment cap to prevent overbooking of any single course. The SemesterRegistration entity links a student to their program, academic year, semester, and the specific list of registered courses, along with a computed TotalCredits field used to enforce minimum/maximum credit limits per semester. A Timetable entity manages the scheduling of each course, specifying the day of week, start and end time, and venue, which is essential for both students and faculty to avoid scheduling conflicts. This module also handles faculty assignment to courses, ensuring a faculty member's teaching load is tracked. A key challenge in this module was preventing double-booking of venues and time slots in the timetable, which required additional validation logic in the Service layer before persisting a new timetable entry. Status fields (Registered, Confirmed, Withdrawn) allow tracking of whether a student has finalized their semester registration or withdrawn from it. This module integrates closely with the Attendance module since attendance is recorded per registered course.

### 4. Module 4.4 — Attendance & Academic Progress Tracking

This module enables faculty to record lecture-level attendance for every student enrolled in their course, and automatically derives meaningful academic insights from that raw data. The AttendanceRecord entity stores a single entry per student per lecture date, with a status of Present, Absent, Late, or OfficialDuty. Rather than requiring manual percentage calculation, the system maintains an AttendanceSummary entity that aggregates TotalLectures and Attended counts per course per semester, and computes an AttendancePercent value. A ShortageFlag boolean is automatically set to true whenever a student's attendance falls below the institution's defined threshold (commonly 75%), which then feeds into the Notifications module to alert both the student and faculty. Separately, the AcademicStanding entity tracks each student's CGPA per semester and assigns an overall status — Good, Probation, Detained, or Expelled — based on configurable academic performance rules. This module required designing efficient aggregation logic so that attendance summaries update correctly without needing to recalculate from scratch on every single attendance entry, which is important given the system needs to support 30,000+ concurrent users during peak periods. The Service layer contains the core business logic for percentage calculation and threshold checking, and this was one of the more heavily unit-tested modules due to its dependency on accurate arithmetic and edge case handling (e.g. zero lectures held, all absences).

### 5. Module 4.5 — Examination & Results Management

This module manages the complete examination lifecycle, from scheduling to final result publication. The ExamSchedule entity allows the Examination Controller to create internal, end-semester, practical, or supplementary exams for a given course, specifying the exam date, start time, duration, and venue, with hall allocation logic ensuring no double-booking of examination halls. Once exams are conducted, faculty members submit grades through the GradeRecord entity, which captures marks obtained against the maximum marks and computes a letter grade. Grades pass through a defined status workflow — Draft, Submitted, Published, ReEvaluationRequested, Revised — giving students the ability to formally request re-evaluation if they believe their grade was incorrectly assessed, and faculty the ability to revise and resubmit. Once results are finalized, a ResultCard is generated per student per semester, aggregating the number of courses appeared, computing the SGPA, and flagging any backlogs (failed courses) that need to be cleared in future semesters. This module is marked as high-priority for availability (99.9% uptime) since result publication periods see extremely high concurrent traffic from students checking their scores. The Service layer enforces strict validation to prevent grade tampering after publication, and a full audit trail is maintained for every grade submission and revision, tying back into the AuditLog from the Identity module.

### 6. Module 4.6 — Fee & Scholarship Management

This module handles all financial transactions between the institution and its students. The FeeInvoice entity is generated each semester per student, combining multiple configurable fee heads — Tuition, Hostel, Library, Lab, and Activity fees — into a single TotalAmount, with a DueDate by which payment is expected. The FeePayment entity records each payment transaction against an invoice, capturing the amount paid, payment date, payment mode (Online, DD, Cash, BankTransfer), and a unique receipt number for record-keeping. Since multiple partial payments can be made against a single invoice, the system tracks invoice status as Generated, Paid, PartiallyPaid, Overdue, or Waived, and the Accounts Dashboard surfaces a real-time list of overdue accounts for follow-up. The Scholarship entity manages merit or need-based scholarship awards from Government, Institutional, or External sources, and when a scholarship is approved, the ScholarshipAdjusted field on the relevant invoice is updated to reduce the NetPayable amount the student owes. A key design decision in Phase 1 was that all payments are recorded manually or via internal entry rather than integrating directly with an online payment gateway, which is deferred to Phase 2 — this significantly simplified the initial implementation while still providing full fee tracking capability. This module required careful decimal/currency handling in the Service layer to avoid rounding errors, and unit tests specifically cover edge cases like scholarship amounts exceeding the total fee.

### 7. Module 4.7 — Hostel & Campus Facilities Management

This module manages physical campus resources — hostel accommodation and shared facilities. The HostelRoom entity maintains an inventory of all rooms across hostel blocks, tracking capacity, current occupancy, room type (Single, Double, Triple), and availability status (Available, Occupied, Maintenance). When a student requests hostel accommodation, the HostelAllotment entity links them to a specific room for an academic year, recording check-in and check-out dates, with a status that reflects whether the allotment is Active, VacatedEarly, or Completed. The Service layer includes validation to prevent allotting a room beyond its capacity, which required careful concurrency handling since multiple allotment requests could come in around the same time during peak hostel registration periods. Separately, the FacilityBooking entity allows students or faculty to request use of shared campus resources such as seminar halls, labs, or sports infrastructure, specifying the booking date, time slot, and purpose. Bookings move through a Requested, Approved, Rejected, or Completed status workflow, with hostel/facility admins responsible for approving or rejecting requests based on availability. A notable challenge in this module was designing the data model to efficiently check for time-slot conflicts when approving facility bookings. This module integrates with the Notifications module to alert students when their hostel allotment or facility booking status changes.

### 8. Module 4.8 — Notifications & Alerts

This module acts as the central communication layer of CampusCore, ensuring users are kept informed about important events across all other modules without needing to actively check each one. The Notification entity stores a message tied to a specific UserID, categorized by type — Admissions, Attendance, Examination, Fee, Hostel, or Academic — which allows the frontend to group and filter notifications meaningfully. Each notification has a Status field (Unread, Read, Dismissed) so users can track what they've already seen, and a CreatedDate for chronological ordering. This module is triggered by events happening in other modules: for example, when an admission status changes, when an attendance shortage is flagged, when a fee invoice becomes overdue, when grades are published, or when a hostel allotment is confirmed. In Phase 1, all notifications are scoped to be in-app only, meaning SMS and email integrations are explicitly out of scope and deferred to a future phase — this kept the implementation lightweight while still providing the core alerting functionality students and faculty need. The Service layer for this module is intentionally kept simple, mainly handling creation, retrieval, and status updates, since the bulk of the "intelligence" (deciding when to send a notification) lives in the business logic of the originating module. Unit tests for this module focus on verifying that notifications are correctly categorized and that status transitions (Unread → Read → Dismissed) work as expected.

### 9. Database Design

This task covered designing the complete relational schema underpinning all 8 modules, comprising 18 interconnected tables. The design process began with identifying core entities (User, Program, Course) and then mapping out the relationships and foreign keys needed to connect admissions data through to academic records, financial records, and facility usage. Particular attention was paid to normalization to avoid data duplication, while still keeping query performance in mind given the system needs to support 30,000+ concurrent users during peak periods like semester registration and result publication. Status fields were deliberately designed as constrained enumerations (e.g. Active/Inactive, Present/Absent/Late/OfficialDuty) rather than free text, to enforce data integrity at the application level. Foreign key relationships were carefully planned — for instance, linking FeeInvoice to StudentID and AcademicYear, or GradeRecord to both ExamID and StudentID — to support efficient querying for dashboards like the Accounts Dashboard's overdue account list. The schema was designed to be database-agnostic, compatible with MySQL, PostgreSQL, or SQL Server, since the architecture specifies flexibility in database choice. This task also involved planning for multi-campus scalability, ensuring tables could support campus-scoped data partitioning without requiring a schema redesign later. The finalized schema was documented and used as the single source of truth for generating JPA entity classes in the codebase.

### 10. REST API Development

This task involved building the full three-layer backend architecture — Controller, Service, and Repository — for all 8 modules using Spring Boot. Each module's Controller layer exposes RESTful endpoints following standard HTTP conventions (GET for retrieval, POST for creation, PUT for updates, DELETE where applicable), with consistent response structures and appropriate HTTP status codes (200, 201, 400, 404, 409, 500). The Service layer houses all business logic, including validation rules, status transition checks, and calculations (like attendance percentages and fee net payable amounts), keeping the Controller layer thin and focused purely on request/response handling. The Repository layer leverages Spring Data JPA, allowing most CRUD operations to be auto-generated, while custom queries using @Query annotations were written for more complex data retrieval needs, such as fetching all overdue invoices or students with attendance shortages. DTOs (Data Transfer Objects) were introduced between the Service and Controller layers to control exactly what data is exposed to API clients, preventing internal entity details from leaking into responses. A global exception handler using @ControllerAdvice was implemented to catch and format errors consistently across all modules. This task represented the bulk of the development effort and required close coordination between modules, since several APIs depend on data from other modules (e.g. Fee invoicing depends on SemesterRegistration data). API documentation was maintained alongside development to keep endpoint contracts clear for testing and future frontend integration.

### 11. JUnit Test Cases

This task focused on writing comprehensive unit tests using JUnit 5 for the Service layer logic across all 8 modules, since the Service layer contains the bulk of the business rules that need verification. Each test class follows the standard Arrange-Act-Assert pattern: setting up test data, invoking the method under test, and asserting that the output matches expectations. Test cases were written not just for the "happy path" but specifically targeted edge cases and failure scenarios — for example, testing that requesting a course registration beyond the maximum credit limit throws an appropriate exception, or that fetching a non-existent record returns a 404-style ResourceNotFoundException rather than crashing. Particular focus was given to modules with complex calculations, such as Attendance percentage computation and Fee net payable calculation, since arithmetic bugs in these areas would directly impact students. Test coverage was tracked to ensure all critical business logic paths were exercised, including boundary conditions like exactly 75% attendance (the shortage threshold) and zero-amount scholarships. Writing these tests early in the development cycle helped catch several logic bugs before they reached integration testing, particularly around status transition validation in the Admissions and Examination modules. This task also involved setting up the test project structure and Maven test dependencies (spring-boot-starter-test) to ensure tests run consistently across different development environments.

### 12. Mockito Mocking

This task involved using Mockito to isolate the Service layer from the actual database during unit testing, which was essential for keeping tests fast, repeatable, and independent of any real data. Repository interfaces for each module (e.g. CourseRepository, FeeInvoiceRepository) were mocked using the @Mock annotation, and the corresponding Service class under test was instantiated with these mocks automatically injected via @InjectMocks. The when().thenReturn() pattern was used extensively to simulate specific database responses — for instance, configuring a mocked repository to return a specific Course object when findById() is called with a given ID, without ever touching a real database. Similarly, when().thenThrow() was used to simulate failure scenarios, such as a repository call that would normally indicate a record was not found, allowing verification that the Service layer correctly translates this into the appropriate custom exception. The verify() method was used throughout to confirm that repository methods were called the expected number of times with the expected arguments, which helped catch subtle bugs where, for example, a save() operation was accidentally being triggered twice. This mocking approach proved especially valuable for testing modules with complex multi-step business logic, like the Admissions status transition workflow, where a real database round-trip for every test would have made the test suite slow and unwieldy. Overall, Mockito-based testing significantly increased confidence in the correctness of business logic before any integration or manual testing began.

### 13. Controller Layer Testing

This task covered testing the REST API layer using Spring's MockMvc framework, which simulates HTTP requests without needing to start a full running server, making these tests fast while still verifying the complete request-response cycle. Using the @WebMvcTest annotation, only the web layer for a given controller was loaded into the test context, with the underlying Service layer mocked using @MockBean to keep these tests focused purely on HTTP concerns rather than business logic. Test cases verified that endpoints return the correct HTTP status codes for various scenarios — 200 OK for successful retrievals, 201 Created for successful resource creation, 404 Not Found when a Service layer call throws a ResourceNotFoundException, and 400 Bad Request for malformed input. The jsonPath() assertions were used extensively to verify that the JSON response body contains the expected fields and values, ensuring the API contract matches what frontend developers and API consumers would expect. Particular attention was paid to testing POST and PUT endpoints with various request body payloads, including missing required fields, to confirm that validation annotations on DTOs were correctly triggering 400 errors. This task also verified that authentication and authorization were properly enforced at the controller level, ensuring endpoints reject requests without a valid JWT token or with insufficient role permissions. Controller-level tests complemented the Service-layer Mockito tests by catching issues specific to serialization, routing, and HTTP semantics that wouldn't be caught by Service-layer tests alone.

### 14. Integration Testing

This task involved testing complete end-to-end workflows that span multiple modules, verifying that the system behaves correctly when modules interact with each other as they would in real usage. Key workflows tested included the full admission-to-enrollment journey (application submission → shortlisting → document verification → offer issuance → enrollment), the semester lifecycle (registration → course allocation → attendance marking → exam scheduling → grade submission → result publication), and the financial workflow (fee invoice generation → scholarship application → payment recording → overdue flagging). Unlike unit tests which mock dependencies, integration tests used an in-memory or test database to verify actual data persistence and retrieval across the full Controller-Service-Repository stack. This testing phase surfaced several issues that unit tests alone could not catch, particularly around foreign key constraints and cascading status updates — for example, ensuring that when a SemesterRegistration is withdrawn, dependent records like Timetable entries and AttendanceSummary calculations behave correctly. Testing also covered the Notifications module's integration points, verifying that events in other modules (like a published result or an overdue fee) correctly trigger the creation of corresponding notification records. Performance-related integration testing was conducted to validate the system's behavior under simulated concurrent load, given the non-functional requirement to support 30,000+ concurrent users during peak periods. This task was critical in validating that the modular design, while developed somewhat independently, comes together as a cohesive, reliable system.

### 15. Documentation

This task covered preparing all project documentation needed for trainer review, team handoff, and future development reference. This included the primary README files explaining each module's features, database entities, and REST API endpoints; a detailed backend code flow document illustrating how a request travels through the Controller-Service-Repository-Database layers; and a dedicated testing guide explaining the JUnit and Mockito approach with annotated code examples for trainer walkthroughs. Documentation also covered the system's non-functional requirements (performance, security, scalability, availability, maintainability, observability) and explicitly listed assumptions and constraints for Phase 1, such as the exclusion of payment gateway integration and biometric attendance, to set clear expectations about project scope. A module-wise task tracker was created to log development progress, including start and end dates for each task and a space to record remarks or issues encountered, supporting project management and retrospective review. Architecture diagrams and ASCII flow charts were included throughout to make technical concepts easier to explain verbally during presentations, particularly the request flow and overall system workflow diagrams. Care was taken to keep documentation in Markdown format for easy version control alongside the codebase, while remaining straightforward to convert into other formats like Word or PDF if required for formal submission. This task was treated as an ongoing activity throughout development rather than a final step, ensuring documentation stayed accurate as the implementation evolved.
